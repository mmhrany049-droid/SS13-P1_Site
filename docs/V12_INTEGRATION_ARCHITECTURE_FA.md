# معماری ارتباط داخلی سامانه SS

## هدف

SS یک وب‌اپ واحد است؛ نه چند برنامه که داده را با کپی‌های نامطمئن ردوبدل کنند. این نسخه بر پنج اصل بنا شده: هویت واحد در API، مالکیت روشن هر داده، حداقل اشتراک‌گذاری لازم، انتقال idempotent با صف آفلاین، و projection جدا برای گزارش سازمان بدون افشای سابقه خصوصی.

## نقشه سامانه‌ها و مرجع حقیقت

| بخش | هدف | مرجع حقیقت | مصرف‌کننده |
|---|---|---|---|
| پوسته و هویت (`shell/Root`, `/api/auth/*`) | ورود واحد، نقش و نشست | کاربران، عضویت‌ها و نشست‌های API | همه صفحات |
| فضای شخصی (`/today`) | تمرین، مرور، برنامه، آزمون و تنظیمات | جزئیات در state محلی؛ رخدادهای همگام‌شده در API | خود دانش‌آموز |
| صف آفلاین | نگهداری و ارسال دوباره ثبت‌ها بدون دوباره‌شماری | IndexedDB/localStorage و `Idempotency-Key` | API مطالعه |
| دامنه/رویداد | منطق مطالعه و گزارش روزانه | `events` مرجع؛ `proj_today` و `org_today` قابل‌بازسازی | داشبورد دانش‌آموز و سازمان |
| فضای سازمان (`/workspace`) | اعضا، برنامه کلاس، import و گزارش | API محدود به `organizationId` | کاربر مجاز همان سازمان |
| `.sspack` | انتقال آفلاینِ داده انتخابی | بسته با checksum و رضایت‌های نوع‌به‌نوع | import و رکوردهای اشتراکی |
| پل legacy | سازگاری نصب‌های قبلی | API و داده‌های قدیمی global | تک‌سازمانی؛ در چندسازمانی بسته است |

## مسیرهای ارتباط ساخته‌شده

### مطالعه تا گزارش سازمان
`/today` → صف آفلاین → `POST /api/study/sessions` → رویداد `study.session.logged` با `organizationId` → ثبت اتمیک رویداد و projection شخصی/سازمانی → `GET /api/workspace/progress`.

API از کلید idempotency برای جلوگیری از رکورد تکراری استفاده می‌کند. گزارش میزکار فقط خلاصه روزانه کاربران همان سازمان را نشان می‌دهد، نه پاسخ‌ها یا یادداشت‌های خصوصی. رخدادهای قدیمی بدون سازمان فقط وقتی به projection سازمانی بازسازی می‌شوند که کاربر دقیقاً یک عضویت دانش‌آموزی فعال داشته باشد؛ داده مبهم به سازمانی نسبت داده نمی‌شود.

### بسته دانش‌آموز تا اطلاعات قابل‌مصرف میزکار
`buildPack()` → پیش‌نمایش import → اعمال تراکنشی → `integration_records` با `organizationId`, `ownerId`, `kind`, `sourceJobId` و وضعیت → نمایش خلاصه‌ی داده در «پیوند مطالعه و کلاس».

کتاب، نتیجه، آمار، پرونده، خلاصه و درخواست فقط در صورت وجود رضایت مربوط وارد می‌شوند. گزارش معمولی full-state پشتیبان را برنمی‌گرداند. checksum فقط خرابی تصادفی را تشخیص می‌دهد و هویت سازنده را ثابت نمی‌کند؛ بسته‌ی حساس باید از نظر هویت/رضایت در فرایند مرکز هم بررسی شود.

### برنامه رسمی کلاس و آزمون
API برنامه‌ی منتشرشده وجود دارد، اما نمایش و تطبیق آن با برنامه‌ی شخصی هنوز در رابط `/today` پیاده نشده است. اتصال بعدی باید read-only شروع شود، پایه/رشته/کلاس را تطبیق دهد، سپس فقط پیشنهاد غیرقطعی بسازد؛ نباید برنامه‌ی شخصی را بی‌اجازه بازنویسی کند. آزمون آنلاین نیز هنوز پشت feature gate است.

## مرزهای اعتماد

- فهرست/اعمال/بازگردانی import فقط در سازمان job مجاز است؛ رویدادهای workspace هم به سازمان جاری محدود شده‌اند.
- رویدادهای میزکار فقط metadata و نام کلیدهای payload را برمی‌گردانند، نه محتوای خام.
- پشتیبان محلی راز ورود، PIN hash، recovery hash و credential مرکز قدیمی را صادر نمی‌کند؛ عکس‌ها فقط پس از تأیید restore ذخیره می‌شوند.
- همگام‌سازی روی آخرین state کاربر اعمال و تغییرات هم‌زمان merge می‌شود.
- ماژول‌های legacy از پایگاه چندسازمانی عبور نمی‌کنند؛ تا مهاجرت کامل endpointها در آن حالت ۴۱۰ برمی‌گردد.

## APIهای اتصال

| مسیر | کارکرد |
|---|---|
| `POST /api/study/sessions` | ثبت idempotent جلسه‌ی خود دانش‌آموز |
| `GET /api/today` | خلاصه شخصی هفته |
| `GET /api/workspace/progress` | فهرست خلاصه دانش‌آموزان قابل‌دسترسی در سازمان |
| `GET /api/workspace/progress/:id` | خلاصه و داده‌های اشتراکی همان دانش‌آموز/سازمان |
| `GET /api/workspace/events` | metadata رویدادهای سازمان جاری |
| `GET /api/workspace/events/verify` | مقایسه projection سازمانی با replay |
| `/api/workspace/imports*` | پیش‌نمایش، اعمال و rollback واردسازی tenant-scoped |
| `GET /api/schedule` | برنامه‌های منتشرشده؛ هنوز مصرف خودکار در planner ندارد |

## کارهای باقیمانده برای شبکه کامل

- انتقال پیام، ایمیل، اعلان، مدیریت دانش‌آموز و صفحات قدیمی از state global به endpointهای tenant-scoped.
- جایگزینی پروتکل bulletin قدیمی با تبادل نسخه‌دار روی identity واحد.
- مدیریت رضایت، تاریخچه اشتراک، حذف داده و سیاست retention.
- اتصال پایه/رشته/کلاس به برنامه رسمی، برنامه‌ریز و آزمون.
- dispatcher واقعی outbox، PostgreSQL، تست مرورگر/E2E، rate-limit مشترک چندنمونه‌ای و تست بار.

## سنجش پذیرش این مرحله

- تست Node: ۶۷/۶۷ قبول؛ شامل جریان مطالعه تا گزارش سازمان، جداشدن import بین سازمان‌ها، حفظ رکوردهای رضایت‌دار و rollback.
- `node scripts/check.mjs` موفق.
- build production در محیط بررسی اجرا نشد: `npm` و وابستگی‌های bundler نصب نیستند. پس از دریافت کد: `npm install` و `npm run build`؛ فایل‌های `apps/web/dist` باید با build جدید جایگزین شوند.

## تکمیل بودجه‌بندی دقیق آزمون (۱۴ اکتبر ۲۰۲۶)

موتور پوشش سؤال اکنون از rangeهای سراسری/فصلی کتاب، `span` فصل و بخش، وضعیت تدریس و پاسخ‌های ثبت‌شده در جلسه‌های مطالعه استفاده می‌کند. شماره سؤال یکتا شمرده می‌شود، بنابراین تکرار یک تست در چند جلسه شمار «زده‌شده» را زیاد نمی‌کند؛ آخرین پاسخ همان شماره برای شمار درست/غلط ملاک است و پاسخ سفید جدا ثبت می‌شود. نتیجه‌ی تجمیعی آزمون که شماره‌ی تک‌سؤال ندارد در شمار دقیق زده‌شده قرار نمی‌گیرد و به‌صورت جداگانه گزارش می‌شود.

اگر rangeها ناقص باشند، رابط به‌جای ساختن عدد قطعی، تعداد سؤال‌های شماره‌دار و مبحث‌های بدون بازه را نشان می‌دهد. اگر همه برگ‌های یک فصل/بخش انتخاب شده باشند و span آن معلوم باشد، کل سؤال‌های آن محدوده دقیق شمرده می‌شود؛ تخصیص بین برگ‌های بی‌بازه فقط «برآورد» است. تغییر range، split مبحث، تدریس و ثبت تست بدون بازسازی آزمون روی آمار و پیش‌بینی اثر دارد. شمار تدریس بر اساس نشان‌های «تدریس‌شده» در ساختار شخصی کتاب است، نه حضور در کلاس.
